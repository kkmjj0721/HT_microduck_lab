# 并发协作与审查规范

## 1. 适用范围

本规范适用于多人或多个编码代理共同开发，也适用于单个实现者配合独立审查者的任务。开发阶段与模块边界见 [开发工作流设计](development_workflow.md)。

并发以职责可拆分、文件归属明确和接口已约定为前提。独立的模块实现、资料检查和稳定改动的审查可以并发；同一文件的修改、依赖上一步产物的操作及最终集成按顺序执行。简单修改不为凑并发拆分任务。已登记主任务的状态仅在 [任务表](development.md) 维护，同时最多一个主任务进行中；并发子工作属于同一主任务。

## 2. 角色与并发规模

| 角色 | 职责 | 交付内容 |
| --- | --- | --- |
| 统筹者 | 明确需求、设计与分工，维护接口约定，协调共享资源，集成并验收 | 任务清单、最终差异、整体验证结果和审查结论 |
| 实现者 | 在分配范围内实现并验证，及时报告接口变化或阻塞 | 文件清单、行为变化、检查结果和未解决问题 |
| 独立审查者 | 阅读需求、代码和证据，报告问题并复核修复 | 有位置和依据的审查意见，以及复核结论 |

建议从一个统筹者、最多两个并发实现者和一个独立审查者开始，实际并发上限服从可用工具、任务规模与资源限制；没有独立工作时及时收敛并发。角色可以分阶段轮换，但同一项改动的作者不能作为该改动的独立审查者。

实现者不自行扩大任务或继续分派子代理；需要调整分工时由统筹者安排。审查者默认只读，可以运行不会覆盖交付文件的检查；若需要修复，由统筹者交回实现者处理。

## 3. 分派前明确任务边界

大功能在 [功能设计](design/TEMPLATE.md) 中记录分工，小任务可以在任务说明中记录以下内容：

| 字段 | 必须说明的内容 |
| --- | --- |
| 任务标识与负责人 | 可区分的任务名称、唯一负责人、实现或审查角色 |
| 目标与验收 | 本任务需要交付的实际行为和完成条件 |
| 允许修改的文件 | 尽量列出具体文件；目录授权需确保与其他任务不重叠 |
| 只读上下文 | 相关设计、接口、已有实现和用户修改 |
| 前置依赖 | 需要先确定的接口、配置或其他任务产物 |
| 接口约定 | 输入输出、维度、单位、类型、设备、异常与兼容性要求 |
| 验证与资源 | 需要执行的检查、环境、设备和运行预算 |
| 交回要求 | 文件清单、验证证据、接口变化和遗留问题 |

例如，新增任务时可先约定配置与观测接口，再由不同实现者分别编写任务逻辑和算法适配；运行入口在组件接口稳定后装配。该示例只说明依赖关系，不代表仓库已存在相应实现。

## 4. 共享工作区与同步

### 文件归属

- 默认可共享同一工作区，但每个文件在同一时刻只能有一个修改者。只读查看不受此限制，读取到的阶段性内容不能直接当作最终审查结果。
- `AGENTS.md`、公共配置、依赖声明和设计文档等共享文件由统筹者指定唯一修改者；其他任务交回修改建议，由该修改者统一更新。
- 需要修改范围外的文件时，先向统筹者说明原因，由其调整归属后再修改，不直接覆盖其他任务的内容。
- 不因某项检查失败就回滚整个工作区；先识别失败与哪些修改有关，保留用户及其他实现者的工作。
- 共享工作区内不并发切换分支或执行 Git 写操作。本项目默认不提交、推送、合并或发布，并发开发不改变用户的授权边界。

### 接口与状态同步

- 统筹者维护统一接口约定。接口改变时通知所有使用方，更新设计并暂停依赖旧接口的相关实现，其他独立任务继续进行。
- 无依赖的任务可以立即推进；需要接口约定的任务在约定明确后推进；需要实际实现产物的集成检查在依赖就绪后执行。
- 子任务使用“待开始、进行中、受阻、待审查、修复中、待复核、已完成”等状态。受阻时报告具体依赖，不静默等待，也不凭空补造接口。
- “实现完成”只表示可以交给审查，不能直接等同于“整体功能完成”。审查和验证结束后，统筹者更新最终状态。

### 运行资源

- 并发任务使用不同的临时路径和实验输出目录，不共同覆盖日志、检查点或生成文件。
- GPU、仿真环境和远程端口由统筹者按实际资源安排；共享资源不足时串行执行重型检查，不让各代理独立启动完整训练。
- 验证记录应说明所检查的文件状态；检查过程中相关文件被修改时，由统筹者判断并重新执行受影响的检查。

独立工作区只在确有隔离需求时使用；需要移交未提交内容时可以交回文件或补丁，不把创建提交当作并发协作的前置条件。

## 5. 子任务交回与集成

实现者交回内容必须包含：

1. 实际修改的文件及其职责。
2. 关键行为与接口变化，是否偏离原设计。
3. 已运行检查的命令、环境和结果，以及未运行项目及原因。
4. 仍需其他任务处理的依赖和已知问题。
5. 关键技术判断的参考出处与适用差异，区分本项目已验证事实、论文依据、参考项目依据和推断／待验证假设，并说明后者的验证方法。

统筹者先确认文件归属与接口一致，再按依赖顺序装配组件。共享工作区中的“集成”指核对和连接已产生的改动，不需要执行 Git 合并。集成后检查全量改动、遗漏的新文件和跨模块行为，再交付最终审查与验证。

## 6. 审查时机与输入

- 大功能在编码前检查设计中的模块边界、接口、并发分工和验收标准，发现关键缺口时先修正设计。
- 开发期间可以审查已经稳定的文件，与其他不相关文件的实现并行；审查期间该批文件保持稳定，发现变化时重新核对差异。
- 最终审查覆盖全部交付文件及必要上下文，包括新增、删除、重命名和未跟踪文件。不能仅凭 `git diff` 的已有跟踪文件输出判断范围完整。
- 提供需求、设计、文件清单、参考出处、已执行验证和已知限制。审查者读取实际内容，不仅依赖实现者的摘要或“检查通过”声明。
- 若审查或验证后又改动文件，只复核新增修改及其影响；不无理由重复已完成的无关检查。

## 7. 审查重点与问题格式

审查先判断正确性和验收，再判断结构与可维护性：

1. 实现是否满足需求，有无遗漏或不必要的范围扩大。
2. 模块职责与依赖方向是否符合设计，入口是否保持轻量。
3. 观测、动作、奖励、重置等相关逻辑，以及形状、单位、归一化、设备和数据类型是否一致。
4. 配置、检查点和资源路径是否兼容，异常及边界情况是否正确处理。
5. 验证是否覆盖变化，实验结果是否能追溯到实际代码和配置。
6. 中文注释与文档、英文日志、脚本文件头和用法是否符合项目规范。
7. 关键技术判断的论文与参考项目出处是否可追溯、是否实际支持判断，相关版本与适用差异是否明确；本项目验证、外部结果与推断是否区分，待验证假设是否有对应验证方法。
8. 论文或参考项目复现是否符合 [复现基准与缺失细节处理规则](development_workflow.md#论文与参考项目复现的基准与缺失细节处理)：指定基准与实现是否对应，用户未要求修改的部分是否保持一致，理解不清的问题是否已向用户询问并明确，补充细节是否有依据，需用户确认的选择是否已获确认，复现基线是否保留，运行验证与效果验收是否区分。

只报告有依据、可采取行动的问题；推测标为待核实，不为增加问题数量编造缺陷。审查意见包含问题编号、严重程度、文件与行号、触发条件、影响、依据及修复建议。

| 严重程度 | 判断依据 | 完成要求 |
| --- | --- | --- |
| 阻塞 | 关键行为错误、流程不可用、重要接口不兼容，或缺少必要验证以判断是否满足验收 | 必须修复或补齐证据，并完成复核 |
| 一般 | 可复现的局部缺陷或违反明确规范，影响本次交付质量 | 交付前修复并复核 |
| 建议 | 不影响正确性和既定验收的改进，或个人风格偏好 | 不阻塞交付，可记录后续处理 |

与本次修改无关的已有问题单独注明，不混入本次必须修复的事项。有争议时由统筹者对照需求、代码和可复现证据判断，不能为了通过审查降低既定验收标准。

## 8. 修复、复核与最终结论

1. 统筹者将问题分派给相应实现者，保持文件归属唯一；不同文件的修复可以并发。
2. 实现者逐项说明修改位置、处理方式和验证结果，将问题置为待复核。
3. 审查者检查修复及其影响，确认解决后关闭问题；未解决时说明缺失证据并继续修复。
4. 统筹者检查最终完整差异和集成验证，确认交付内容没有超出已审查范围。

大功能或跨模块接口变更使用 [审查记录模板](review/TEMPLATE.md) 记录过程；小范围改动可在交付回复中保留简要结论。结论区分“独立审查通过”“自审完成”“审查未完成”，并列出未验证内容及未解决问题。没有发现可确认问题时如实说明，不把审查通过描述为不存在任何风险。

大功能或跨模块接口变更仅在验收相关问题关闭、必要验证完成且独立审查通过后标记完成。审查与复核属于内部开发流程，不要求用户逐轮确认，也不授予 Git 提交或发布权限。

统筹者确认所有代理和检查进程结束后，再按 [项目产物约束](../AGENTS.md#本项目的技术与产物约束) 清理本次临时文件及字节码；保留失败现场至排查结束，不删除用户已有实验产物。
