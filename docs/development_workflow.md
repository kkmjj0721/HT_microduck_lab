# 开发工作流设计

## 1. 目标与现状

本流程将项目开发规范落实为可执行的开发步骤，覆盖需求确认、参考资料核查、模块设计、并发协作、代码实现、实验验证、独立审查和交付验收。实现类任务以实际代码和验证结果交付，文档按变更影响维护。

项目使用 mjlab 1.6.0，机器人、执行器与任务位于独立包 `src/ht_microduck/`，统一训练算法来自根目录的 `rsl_rl/`（rsl-rl-lib 5.4.2 完整副本），`duck-train`、`duck-play` 是官方入口薄封装。安装与检查见 [安装配置](setup.md)；具体能力以相关源码和实际验证为准。

本文件负责开发规则与执行流程，运行依赖由 [安装文档](setup.md) 维护；已有阶段、任务状态与历史证据由 [阶段与任务记录](development.md) 维护。通用规则完整沿用参考工作流，目录、入口与本项目产物约束按实际仓库适配。

| `docs/review/TEMPLATE.md` | 大功能或跨模块接口变更的审查记录模板 |
| `README.md` | 提供项目介绍、最短可用示例和必要文档链接 |
| `docs/development.md` | 维护已有阶段依赖、任务状态和必要结果索引，小修改不强制新增记录 |

| `docs/archive/` | 保留已结束任务及历史完成记录的原始措辞和当时结论 |

通用约束以 `AGENTS.md` 为准；本文件补充执行流程，功能设计文档记录具体决策。修改通用约束时检查相关文档，仅更新受影响内容。

### 按改动选择流程与文档

| 改动情况 | 执行方式 | 文档处理 |
| --- | --- | --- |
| 小范围修复、参数调整、局部重构 | 定位问题，直接修改，执行受影响检查并自审 | 结果在回复中说明；已有说明仍准确时不改文档，不新建记录 |
| 用法、安装步骤、配置含义或对外接口变化 | 实现并验证新行为，检查已有示例是否仍可用 | 只更新受影响的现有说明；跨模块接口变化同时按大功能流程处理 |
| 新增任务、算法、训练或部署流程等大功能 | 先明确设计，再实现、验证和独立审查 | 优先补充同主题设计与审查记录，无对应记录时再按模板创建 |
| 用户明确要求文档或流程修改 | 直接修改指定内容，检查链接和规则一致性 | 在现有文件内完成，不为文档修改再新建设计或审查记录 |

README 仅在项目介绍、快速开始示例或必要链接受影响时更新。配置细节在配置定义处维护含义、单位和默认值，专题用法集中在对应说明中；其他位置按需链接，不重复维护参数清单。开发过程、调试记录、逐项改动和单次实验结果不写入 README，也不为每次任务另建进度文档。

## 3. 模块边界与目录归属

| 目录 | 职责与边界 |
| --- | --- |
| `src/ht_microduck/robot/` | 机器人 MJCF、mesh、关节映射、实体初态和碰撞配置；不放奖励或训练循环 |
| `src/ht_microduck/actuator/` | 两类执行器模型、参数来源和 mjlab 生命周期适配；不决定策略动作子集 |
| `src/ht_microduck/tasks/` | 根目录保留注册表与契约；`config/` 放环境/RL/地形配置，统一 `mdp/` 放观测/命令/奖励/终止/重置/课程，`rl/` 放任务 runner 适配 |
| `rsl_rl/` | rsl-rl-lib 5.4.2 完整副本：网络、Storage、PPO、Runner、Logger；训练与回放的实际代码路径，不在此改上游风格 |
| `src/ht_microduck/train_cli.py`、`play_cli.py` | 官方入口薄封装，只做 import 与转发；不承载环境或算法的核心实现 |
| `tools/` | 独立检查工具（模型、契约、环境、文档一致性）；复用包接口，不复制训练核心逻辑 |
| `tests/` | 正式自动化验证；按模块组织，不保留一次性验证脚本 |
| `.artifacts/` | 任务临时验证、检查缓存、构建和解包产物；按所属任务清理 |
| `logs/` | `duck-train` 的默认训练输出根目录；需保留的运行产物 |

现有目录无法合理承载新职责时，先在功能设计中说明新增目录的用途与依赖，再添加实现。不要为了复用少量代码提前建立宽泛的公共模块；当多个任务确有稳定的共享能力时，再提取职责明确的模块。

依赖方向约定：入口脚本装配配置、任务与算法；任务消费配置和资源；算法通过明确的观测、动作及训练接口与任务交互。生产模块不得反向依赖 CLI、`tools/` 或 `tests/`。通用算法不得依赖具体任务。跨模块接口需明确形状、顺序、类型、设备、单位、坐标系、时序、归一化、动作缩放、reset 历史和终止/超时语义。

## 4. 开发流程

### 阶段一：理解需求并检查工作区

1. 阅读 `AGENTS.md`、`README.md`、[阶段与任务记录](development.md)、相关目录的局部规范及已有功能设计；涉及安装或依赖时再读安装文档。
2. 使用 `git status --short --branch`、`git ls-files --others --exclude-standard` 和必要的 `git diff` 确认已有修改、新增未跟踪文件和用户删除的文件，保留与当前任务无关的修改及实验产物。
3. 明确目标行为、输入输出、影响模块和验收方式。能从代码与文档确定的内容直接确认，只有影响实现的关键缺口才向用户询问。
4. 按改动影响选择上表中的流程。实现请求包含完成代码所需的分析、必要设计、适当验证和交付，不在中间阶段停止；用户只要求分析、设计或文档时按指定范围处理。完整训练和大量实验遵守任务的资源范围，提交与发布另需明确授权。

#### 问题分析与参考资料核查

涉及算法、训练现象、控制、仿真或框架行为时，在确定原因和方案前执行以下步骤；小问题可以简要记录，纯文档或格式修改无需额外查论文。

1. 确认本项目事实：阅读相关代码、配置、日志和已有实验，必要时最小复现，记录实际观察与触发条件。先区分已观察到的现象和对原因的解释。
2. 主动查找相关参考项目与论文：先查看 `paper/`、已有设计与可用参考仓库，再按证据缺口补充外部检索。优先阅读论文原文、作者官方实现、上游源码和官方文档；关键算法或机制尽量对照论文与实现，并结合其他相关来源交叉核对，不只依赖记忆或一个相似案例。
3. 阅读直接支持判断的内容并记录出处。论文记录标题、链接或本地路径、版本及章节、公式或页码；参考项目记录地址或本地路径、版本或提交、文件与函数等定位信息。可变网页无固定版本时记录访问日期。搜索摘要、二手解读只作线索；只读到摘要或无法访问原文时明确标注，不能声称已核实全文或实现。
4. 核对适用条件：比较机器人、仿真器、依赖版本、观测与动作定义、单位和实验配置等相关差异，说明哪些方法可以借鉴、哪些需要适配及选择理由。论文描述与实现不一致、不同来源结论冲突时，记录差异与证据，未核实前不擅自断言哪方正确。
5. 按下表区分依据。每个关键判断应能追溯到实际读过的资料或本地验证；由这些依据进一步解释当前问题时，单独标注推断。参考项目使用某种写法只能证明该版本如此实现，不能单独证明其必要性、最优性或对本项目有效。
6. 为影响方案选择的假设给出最小验证方法、预期现象和判定条件，再据此安排修改或实验。未找到充分依据、无法访问资料或尚未验证时，说明已检查的范围、缺口与下一步，不以反复猜测和调参代替查证。

| 依据类型 | 必须说明的内容 | 结论边界 |
| --- | --- | --- |
| 本项目已验证事实 | 代码位置，或实际命令、配置、日志与观察结果 | 静态检查、冒烟运行、训练和评估各自只支持已覆盖的范围 |
| 论文依据 | 论文及具体位置、作者报告的机制或实验结果、相关条件 | 作者的结果不等于本项目已复现；迁移解释另标为推断 |
| 参考项目依据 | 项目、版本或提交、具体实现位置及行为 | 外部项目的实现不等于本项目必须照用或已验证有效 |
| 推断／待验证假设 | 依赖的事实或资料、推理与适用条件、证据缺口及最小验证方法 | 未验证前不写成确定原因、已证明结论或已获得的效果 |

大功能将来源、适用差异和待验证假设写入功能设计；论文阅读与复现的详细记录可放入 `paper/` 并从设计中引用。小问题在分析或交付回复中按需列明，不要求另建文档，也不按固定篇数凑引用。

#### 论文与参考项目复现的基准与缺失细节处理

论文或参考项目复现任务在通用资料核查之外执行以下要求。默认目标是完整遵循用户指定基准的方法、实现和实验设置；除用户明确要求修改的部分外，其余内容完全按照基准执行。提出优化、修正或迁移建议不等于获准修改；用户未明确要求的简化、替换、调参和方法改动，均须先说明并确认。改进或迁移实验须明确其范围，并保留可对照的复现基线。

1. **确定基准与复现范围。** 明确参考项目地址及版本或提交，或论文标题、版本、正文及附录或补充材料，列出要复现的方法和实验，以及用户已指定的修改项、机器人、仿真器和资源限制。先实际阅读相关原文或代码，再形成方案；基准不明确或无法取得必要资料时，说明缺口并向用户询问，不能用摘要、记忆或相似项目代替指定基准后宣称完成复现。
2. **建立基准到实现的对应关系。** 在已有同主题设计或复现记录中列出关键方法与配置，对照原文章节、公式或表格，或参考项目的文件、函数与配置，以及本项目实现位置和验证方式。按任务覆盖网络结构、损失与优化目标、观测和动作、奖励、终止与重置、数据处理、训练阶段、超参数及评估协议。用户明确要求修改的部分逐项记录，其余按基准落实；不得因本地默认配置、个人经验、方便跑通或短期效果而擅自增删奖励、替换损失、简化训练阶段或调整参数，基准中的疑似错误也不能自行修正。
3. **有顺序地补齐未说明的细节。** 论文复现先核查论文附录、补充材料和作者公开配置，再查与该论文对应版本的作者官方实现；参考项目复现先核查指定版本的代码、配置、文档和依赖行为。仍有缺口时查相关项目或向用户询问。借鉴项目时按前述资料核查要求阅读实际代码、固定版本并比较适用条件，记录采用项、选择理由与本地验证方法。仅在不改变基准已明确的内容和用户既定范围、理解清楚且有充分依据时直接补齐；其他项目的做法不能覆盖指定基准，也不能把本地框架默认值当作基准设置。
4. **理解不清先提问，冲突与偏离先确认。** 对用户要求、论文含义、公式、参考代码行为或实现对应关系理解不清时，先说明具体疑问、已查出处及尚不确定的部分，向用户提问，明确后再实施依赖该理解的部分，不自行猜测补全。原文与官方实现不一致、多个来源对影响算法或结果的细节给出不同方案，或关键缺口仍无充分依据时，先列出具体冲突或缺口、已查出处、可执行的候选方案及影响，并给出建议。需要偏离指定基准或既定复现范围时同样先说明原因、具体差异和验证办法。获得用户对该选择的确认后再实施相关部分；已有明确授权直接沿用，不反复询问，等待期间可继续无依赖的工作。自行提出的假设只能作为待确认方案，不能直接写入正式复现配置。
5. **明确工程适配与方法变更的边界。** 文件路径、设备选择或等价 API 替换等不改变数学定义和实验语义的适配可直接处理，并保留必要的映射与验证。机器人或仿真器替换、控制频率变化、观测或动作变更、奖励与训练流程调整等应列明与基准的差异；未在用户既定范围内的变更按上一步确认。不能因名为“工程适配”就默认认定语义等价，理解不清时先询问，条件无法对齐时说明复现结论的适用范围。
6. **保留复现基线，再开展改进。** 复现配置与用户授权的适配、调参或改进实验使用可区分的配置和产物路径，记录每项差异及依据，保留原始配置和已有结果。不将改进配置反向覆盖为复现基线；训练失败或效果不佳时，先核对实现与基准、数据、配置和运行日志，再按有依据的假设安排验证，不能直接靠改算法掩盖偏差。
7. **分别验收实现一致性与实验效果。** 冒烟测试缩减环境数或迭代数时使用单独的测试覆盖配置，标明缩减内容；短跑通过只说明相应运行环节可用。复现验收还需核对上述对应关系，并按约定预算对齐论文或参考项目的指标定义、评估条件和统计口径，记录实际结果与差距。训练预算不足或必要条件无法对齐时，明确未验证范围，不能以“能训练”或一次结果接近基准替代复现完成。

复现大功能在已有设计中维护对应关系、补充细节和经用户确认的差异，并引用实际测试与产物；小范围复现修正可在任务说明或回复中简要记录，不另建文档。交付时区分按指定基准实现的内容、其他来源补充的细节、已授权的适配或改进，以及尚未解决的疑问或缺口；审查按 [并发协作与审查规范](collaboration_review.md) 核对这些内容。

完成条件：可以说明要改变什么、修改哪里、怎样判断完成；关键原因与方案有可追溯依据，尚未确认的解释已标为假设并有验证方法。

### 阶段二：先设计，再实现大功能

以下变化应先形成对应功能设计：

- 新增任务类型、学习算法或机器人平台接入。
- 新增训练、评估、导出或部署流程。
- 跨多个模块调整观测、动作、奖励、配置或持久化接口。
- 引入新的外部依赖或资源体系，显著改变项目结构。

先查找已有同主题设计，仅补充受影响决策；没有对应设计时，复制 `docs/design/TEMPLATE.md` 到 `docs/design/<主题>.md`，删除不适用项。设计应写明必要的参考依据与待验证假设、模块边界、目录归属、关键接口、实施步骤和验收标准，足以指导实现后即继续编码，不反复润色或等待用户逐轮确认。

小范围修复、参数调整、局部重构和文档修订直接实现，不复制设计或审查模板；涉及行为变化时在任务说明或回复中简要说明预期结果。若实际涉及跨模块接口变化等上述大功能范围，则按大功能流程处理。实现发现设计不成立时，只更新相关决策，再继续修改。

存在可独立推进的子任务时，在设计中填写并发分工：负责人、允许修改的文件、前置依赖、接口约定和交付要求。具体执行见 [并发协作与审查规范](collaboration_review.md)。共享接口先确定约定，再并发实现；有实现依赖的步骤按顺序执行。

完成条件：设计中的文件职责、接口关系、协作分工和验证方法足以指导实施。

### 阶段三：按职责实现

1. 先落实配置和接口，再连接任务、算法及运行入口；没有依赖关系的修改可独立进行。
2. 避免在单个脚本中混合参数解析、任务定义、学习算法和可视化。
3. 遵循 [实现简洁性与异常处理约束](../AGENTS.md#实现简洁性与异常处理)，并落实中文注释与文档、英文运行日志、脚本文件头和代码分块约定。
4. 新增配置时写清含义、单位、默认值及适用范围，避免难以追溯的硬编码。
5. 修改观测、动作或策略接口时，同步核对维度、顺序、归一化、数据类型、设备和检查点兼容性。
6. 检查本次修改是否使已有文档失效，仅修正受影响的用法或设计决策；已有说明仍准确时不改文档。新增命令示例必须对应实际入口。
7. 统筹者分派职责不重叠的子任务，实现者仅修改约定文件；共享文件指定唯一修改者，接口变化同步所有相关任务。
8. 子任务完成后交回修改清单、接口变化、验证结果和遗留问题，由统筹者检查完整工作区并集成；不能仅凭子任务完成声明判断整体完成。

完成条件：改动职责明确，接口与文档一致，没有夹带无关重构。

### 阶段四：按影响选择验证

| 改动类型 | 必要验证 | 验收证据 |
| --- | --- | --- |
| 文档和开发规范 | 检查路径、链接、示例与规则一致性；检查差异空白问题 | 文档可查阅，引用有效或明确标注缺失前置条件 |
| 配置或小范围修复 | 执行受影响的现有检查；按需运行导入或启动检查 | 修改生效，原有相关行为可用 |
| 观测、动作、奖励或终止逻辑 | 验证形状、单位、边界值、重置和异常输入 | 关键输入输出符合设计，相关回归验证通过 |
| 训练或算法变更 | 编写或复用训练测试文件，先做配置、初始化与短时冒烟检查，再按下述本地训练规则验证 | 能完成初始化、采样、更新和检查点读写等受影响环节，实际训练时长达标并在结束后统一分析 |
| 策略效果变更 | 使用记录明确的基线、种子、环境和评估配置进行比较 | 按设计中的指标报告结果与波动，不用一次短跑推断收敛 |
| 模型或资源接入 | 检查路径、加载、关节与动作映射及相关物理参数 | 资源可加载，相关映射与任务配置一致 |

本项目已有 `make docs`、`make lint`、`make test`、`make model`、`make lock-check` 等检查入口；文档修改后先执行 `make docs`，交付验收前执行 `make check`，再按影响补充专项检查。Makefile 为每次检查建立独立项目内临时目录，直接执行专项命令仍须显式设置项目内临时与缓存路径，详见 [统一检查命令](development.md#统一检查命令)。`make check` 不覆盖 GPU 动态运行和训练效果，不把尚未运行的命令写成已通过。

低影响、可逆的文档或格式修改不额外编写测试；新增行为和关键修复采用有实际验证价值的测试。检查通过后，仅在出现新修改、失败或未解决风险时扩大或重复验证。

完整训练及大量实验应符合任务明确的资源范围。若完成验证需要超出该范围，先完成可执行的局部验证，并说明尚需的资源和未验证内容。

#### 训练测试文件

需要运行训练验证时，先在 `tests/` 的对应模块目录编写或复用训练测试文件，再通过该文件执行验证。测试文件应满足以下要求：

1. 调用已有任务与算法接口，或启动已有训练入口；只负责配置、启动和结果断言，不复制环境、算法或核心训练循环。
2. 明确任务与算法配置、随机种子、设备、环境数量、迭代或步数上限、超时和独立产物目录，提供实际可执行的命令。测试文件遵循仓库文件头、中文说明和英文运行日志约定。
3. 先运行少量环境、少量迭代的冒烟测试，再显式启动符合下述最低时长要求的本地训练验证；冒烟通过只说明相应运行环节可用，不能替代训练验证。完整训练或耗时实验通过显式参数或单独命令启动，不随普通测试发现自动执行。
4. 按受影响环节设置有实际意义的断言，例如采样和更新完成、关键数值有限、检查点生成且可读取；策略效果另按设计中的评估指标验收。失败或超时应使测试明确失败，并保留诊断日志，不能只打印结果后按成功退出。
5. 测试文件记录可复用的执行命令、配置、预算与验收标准；每次运行的实际配置和结果保存在独立产物目录，交付时引用测试与产物路径。必要的设计或实验结论补充到已有记录，不为每次运行另建 Markdown，也不重复抄写日志。不编造已可执行的命令或已完成的训练结果。

#### 本地训练的等待与结束后检查

1. 启动前确定训练预算、超时、日志与产物路径。本地训练验证的单次实际训练时长至少为 10 分钟（600 秒），不含初始化和训练结束后的等待；按此安排步数或迭代预算及超时，保存完整运行日志和退出状态。短时冒烟检查不能替代该验证，也不能用训练结束后的休眠补足训练时长；启动时仅做必要的初始化确认。
2. 确认启动正常后，全程使用休眠或阻塞等待，将训练进程留在后台或受管理的会话中运行，直到本次训练结束。期间不读取训练日志、指标、检查点或查询设备状态，不持续盯守输出或监控训练；达到 10 分钟后若训练仍在运行，继续等待，不提前分析训练曲线或策略效果。
3. 优先使用进程结束通知或阻塞等待。工具需要分段等待时，使用休眠，醒来仅确认进程是否结束，仍在运行则继续休眠；不在每次唤醒时读取或分析训练日志。休眠不暂停训练进程，也不让训练设备进入系统休眠。
4. 进程结束后，统一检查退出码、测试断言、完整日志、检查点及必要评估，记录实际完成的步数、实际训练时长、总用时和结果，再分析训练曲线与策略效果。实际训练不足 10 分钟的正常结束仅作为短时检查，调整运行预算后重新验证，不能标为训练验证完成。启动失败、异常退出或达到预设超时时可提前排查，并如实记录失败或中断，不把尚在运行或未达最低训练时长的训练标为验证完成。

完成条件：验证覆盖本次改动，成功、失败和未执行项目都有真实记录。

### 阶段五：独立审查与修复复核

1. 为已经稳定的改动安排独立审查者，提供设计、验收标准、实际改动文件和验证证据；新建且未跟踪的文件同样纳入审查。
2. 审查需求符合性、正确性、模块边界、接口兼容性和验证覆盖，同时核对关键引用是否支持相应判断、适用差异是否说明、推断是否误写为事实；按严重程度报告有依据的问题，标明文件位置、触发条件、影响和建议。
3. 实现者修复问题并执行受影响检查，再由审查者复核修复及相关影响；审查者不直接改写被审查文件。
4. 统筹者在各项修改稳定后检查完整差异，执行受影响的集成验证；若集成后出现新修改，重新审查这些修改及其影响。
5. 小范围改动仍需检查差异；若实际没有独立审查者，明确标为自审，不能声称已完成独立审查。大功能或跨模块接口变更未完成独立审查时不得标为完成。

完成条件：验收相关问题已修复并复核，最终交付内容与审查、验证覆盖的内容一致。完整审查规则及记录格式见 [并发协作与审查规范](collaboration_review.md)。

### 阶段六：交付验收

1. 检查最终差异，确认没有无关修改、临时文件或意外纳入的实验产物。
2. 本次需要维护功能设计与审查记录时，补齐受影响的实施状态、实际接口和验证结论，引用现有测试及产物证据；其他改动在交付回复中说明即可。
3. 用中文简要说明修改内容、涉及模块、验证结果、审查结论和必要的限制；区分独立审查、自审及未执行审查。
4. 技术结论在对应判断旁明确标注“本项目已验证事实”“论文依据”“参考项目依据”或“推断／待验证假设”，附关键出处或验证证据及适用范围；同一段混合多种依据时分别说明。只列本次实际涉及的类别；尚未验证的效果、因果解释和迁移假设仍注明验证方法，不用文末一条笼统声明代替逐项区分。
5. 默认把结果留在工作区供用户审阅，不执行提交、推送、合并或发布。设计完成、验证通过和给出提交信息均不代表获得这些操作的授权；用户明确禁止提交时严格遵守。

## 5. 实验记录与训练产物

每次训练运行应记录以下信息，优先使用入口生成的配置快照、运行日志与结果文件，缺失的必要信息补充在对应产物目录中：

- 实验名称、运行标识、开始时间和执行命令。
- 任务、机器人及算法配置快照，随机种子和关键依赖版本。
- 代码版本及工作区是否有未提交修改；工作区有修改时保存相关差异快照，不能只依赖提交编号复现实验。
- 训练步数、环境数量、设备，以及本次关注的指标和基线。
- 检查点、评估结果与日志的实际路径，以及失败或中断原因。

训练产物沿用入口的实际路径；`duck-train` 默认写入 `logs/rsl_rl/<experiment_name>/<运行标识>/`，可通过 `--log-root` 覆盖根目录。不要为了符合示例另建或迁移一套产物目录。开始写入新产物路径前检查相应忽略规则，训练输出、缓存与大体积数据默认不纳入版本控制。

运行日志使用英文；面向开发者的实验说明与结论使用中文。策略指标的定义、评估回合数和通过阈值应在具体功能设计中给出，不在通用流程里设定脱离任务的统一数值。

## 7. Git 提交约定

本项目正式测试、流程/设计/审查文档、锁文件和机器人资源均保持可纳入版本控制，不沿用参考仓库忽略整个 `/tests/` 的仓库特定策略。临时验证、缓存、构建和运行产物按项目内实际目录排除，不全局忽略可能作为资源或测试数据的文件扩展名；新增未跟踪文件同样按实际路径审查。

只有用户明确要求提交时才执行提交，提交信息遵循：

```text
<type>(<scope>): <简短中文描述>
```

| 类型 | 适用修改 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 不改变功能的重构 |
| `perf` | 性能优化 |
| `docs` | 文档 |
| `test` | 测试 |
| `chore` | 配置、依赖、参数等维护 |
| `build` | 构建相关 |
| `ci` | 持续集成与交付配置 |
| `revert` | 回滚 |

类型由实际差异与修改目的决定，不能仅根据文件扩展名判断。`scope` 使用受影响模块的稳定名称，例如 `tasks`、`config` 或 `workflow`。相互独立的改动在获得提交授权后分别组织。
